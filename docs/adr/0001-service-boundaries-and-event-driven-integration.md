# ADR 0001: マイクロサービス境界とサービス間連携方式

## ステータス

Proposed（本PoCの実装スコープ外）。記事の考察パートに残すための設計メモであり、
コードの実装は現時点でAccount serviceのみを対象とする。

## コンテキスト

ネットバンキングWebアプリのバックエンドを何サービスに分割すべきか、という問いから始まった。
最初の誤りがちな前提は「aggregate 1つ = マイクロサービス1つ」だが、これは粒度が細かすぎる。
DDDにおけるサービス分割の単位は境界づけられたコンテキスト（bounded context）であり、
aggregateは「1トランザクションでの整合性境界」というより小さいスコープの概念である。
1つのbounded contextに複数のaggregateが同居してよい。

## 決定

以下の4サービスに分割する。

1. **Account service**（口座）
   `Account` aggregate（残高・凍結・解約のライフサイクル）を所有する。本PoCで実装するのはここまで。
2. **Transfer/Payment service**（振込）
   送金元・送金先という2つの`Account` aggregateにまたがる操作は単一トランザクションで完結しないため、
   独立したプロセスマネージャ（サガ）として持つ。「出金成功→入金試行→失敗時は出金の補償」を調整する。
3. **Query service**（照会）
   プル型。UI/チャネルからの「今の状態を知りたい」という要求に応える。
4. **Notification service**（通知）
   プッシュ型。イベント発生を契機に外部チャネル（push通知・email・SMSゲートウェイ等）へ能動的に配信する。

当初「照会・通知」を1サービスとして構想したが、消費者（内部UI vs 外部配信プロバイダ）と
アクセスパターン（プル vs プッシュ）が異なるため2サービスに分離した。1サービスにまとめると、
本来避けたかった「中央サービスが新チャネル追加のたびにボトルネックになる」構造を一段上で
再生産してしまうため。

## サービス間連携方式：イベント駆動 + セルフサービス登録

Query/NotificationサービスがAccount/Transfer等の各サービスのデータモデルを個別に知り、
対象が増えるたびに改修が必要になる構造は避ける。代わりに以下を採用する。

- 発行側（Account、Transferなど）が共通のイベントバス（EventBridgeを想定）に対して、
  バージョニングされたスキーマでドメインイベントを発行する
- 発行側は自分のイベントスキーマをEventBridge Schema Registryに登録し、
  購読ルール（source / detail-typeでのマッチング）も発行側チームが自分たちのIaCで定義する
- Query/Notificationサービスのコア実装は、新しいイベント発行元が増えても改修不要
  （中央サービスにコードを足すのではなく、周辺のIaC上でルール・スキーマ登録を完結させる）

## トレードオフ

- **結果整合性**：Query側はイベントから構築される読み取りモデルになるため、
  「口座に反映されたはずの取引がまだ照会に出ない」というUXへの説明責任が発生する。
- **スキーマガバナンスは残る**：セルフサービス登録によってコード結合のボトルネックは消えるが、
  イベントエンベロープやスキーマ規約そのものを誰が管理するかという軽量なガバナンスは必要。

## 本PoCの実装スコープとの関係

Lambdaハンドラーの「SQSメッセージをMessageGroupIdでグルーピングし、発生源を問わずコマンドとして
aggregateに適用する」という骨格設計は、この4サービス構想と矛盾しない。Web UIからの直接操作でも、
将来Transfer serviceのサガが発行するコマンドでも同じ経路で扱えるため、
Transfer/Query/Notificationを先取りした特別な作り込みは現時点で不要。
