# ADR 0014: UI E2E(ヘッドレスブラウザ)テストの追加と`e2e/`の`api-e2e/`へのリネーム

## ステータス

Accepted。実装・実デプロイ済みスタックに対して検証済み(`ui-e2e/`、4テスト全件成功、
並列度2で合計約30秒)。

## コンテキスト

[[0012-transfer-customer-api-and-status-query]]決定6(振替/振込Web UI)を実装した後、
実デプロイ環境上でのUIハッピーパス確認(J1・J5〜J10)を、この作業を行っているエージェント
自身がブラウザを操作する手段を持たないために実施できない、というギャップが生じた。

これは新しい発見ではない。`api-e2e/README.md`(当時`e2e/README.md`)のシナリオ対応表は
元々H1-H3・A4/A5のUI固有部分について「このハーネスは生HTTP呼び出しのみで、実際のWeb UI
(ブラウザ)は駆動していない。ブラウザ自動化(Playwright等)が別途必要」と明記しており、
この増分は既に見込まれていた隙間を埋めるものである。

このサンドボックスはWSL環境であり、GUIブラウザは使えずヘッドレスのみが選択肢になる。

## 決定

### 1. `e2e/`を`api-e2e/`にリネームし、ブラウザE2Eは`ui-e2e/`という別の兄弟パッケージに置く

既存の`e2e/`は「実デプロイ済みAPIへの生HTTPリクエスト」しか検証しておらず、ブラウザを
一切駆動していなかった。「api-e2e」という名前の方がこの実態に即しており、「ui-e2e」と
並べたときに「どちらが本流でどちらが派生か」という誤読(ui-e2eがe2eの一部・下位互換の
ように見える)を避けられる。

`infra/README.md`が元々`e2e/`を`infra/`の配下に置かなかった理由(依存関係・役割の独立性、
「デプロイする側」と「デプロイ済みのものを検証する側」を混ぜない)と同じ理由で、
`ui-e2e/`も`api-e2e/`や`web-ui/`の配下ではなく独立したトップレベルパッケージにする——
テストランナー(PlaywrightとJestは別物)・依存関係(ブラウザバイナリを含む)・検証している
層(DOM・イベントハンドラの配線 vs. HTTPレスポンスの中身)がそれぞれ異なるため。

**却下した代替案: Playwrightを`api-e2e/`の`package.json`に同居させる。** テストランナーが
2種類混在し`npm test`が何を指すか曖昧になる(`test:http`/`test:ui`のような分岐が要る)、
`api-e2e/`が元々持っていた「軽量なHTTPクライアントのみ」という依存関係の性質が崩れる、
という理由で不採用。

### 2. 対象はデプロイ済みのCloudFront URLのみ。ローカルdevサーバーは対象にしない

`api-e2e/`が確立した「実デプロイ済みスタック限定・手動/オンデマンド・CI対象外」という
位置づけをそのまま踏襲する。各specは`support/stackOutputs.ts`
(CloudFormation `DescribeStacks`から`WebUiUrl`等を解決)を通じて対象URLを得る——
`api-e2e/`の各シナリオファイルが自前で`fetchStackOutputs`を呼ぶのと同じパターン。

**却下した代替案: `vite dev`のローカルdevサーバーも対象にする。** デプロイ前の反復が
速くなる利点はあるが、テストコードに環境ごとの分岐(対象URLの切り替え)を持ち込むことに
なり、このPoCの規模に対して過剰と判断した。

### 3. ブラウザはヘッドレスChromiumのみ

このサンドボックスがWSLであることに加え、この仕組みの目的はクロスブラウザ互換性の検証
ではなく「実際にユーザー操作が通ることの証明」であるため、複数ブラウザ対応は不要と判断
した。実機確認したところ(`docs/adr/0002`以来一貫している「AWS/ライブラリの挙動は推測
せず検証する」方針、[[verify_aws_specs_before_implementing]]と同じ態度をここでも適用)、
`sudo`権限が無い状態でもこのサンドボックスには既にヘッドレスChromiumキャッシュ
(`~/.cache/ms-playwright`)が存在し起動可能で、実際にデプロイ済みのCloudFront URLを
正しくレンダリングできることを確認した(Debian 13、`libxdamage1`を除く必要な共有
ライブラリは既に揃っていた)。追加のシステムパッケージインストール(`apt-get`)なしで
導入できる。

### 4. テストデータ(口座・顧客セッション)はHTTP直接+`localStorage`注入で用意し、ブラウザで操作する範囲は送金フロー(振替/振込/確認/取消/組戻し)に絞る

口座開設・サインイン画面自体のUI操作は、`web-ui/src/customerSession.ts`が元々非機能な
ダミーである([[0009-web-ui-customer-experience-and-channel-emulation]]決定2)ことに
加え、`api-e2e/`・vitestコンポーネントテストのどちらのカバー範囲にも新たに寄与しない。
`support/seed.ts`が口座開設を生HTTPで行い(`api-e2e/support/testAccount.ts`の
`openFreshAccount`と同じ考え方)、`support/session.ts`が
`BrowserContext.addInitScript`で`customerSession.ts`のlocalStorageスキーマへ直接注入する
ことで、各specは「送金フローだけ」に集中できる——結果整合性の反映待ちを伴う口座開設を
毎回ブラウザ操作で積み上げるより高速で、意図も読み取りやすい。

**却下した代替案: サインイン・口座開設を含め全てブラウザ操作で再現する。** より
「本物のE2E」らしいが、各テストが不要な反映待ちポーリングを重ねて遅くなり、
`api-e2e/`・vitestコンポーネントテストで既にカバー済みの領域(サインイン画面・口座一覧
画面自体の表示ロジック)を重複して検証することになるため不採用。

### 5. カバーするシナリオはJ1・J5/J6(確認・確認前取消)・J9に絞る

`docs/e2e-scenarios.md`のJ2/J3/J4/J8/J10のようなドメイン却下・入力検証系のシナリオは
UI固有の主張を含まない——それらの最終結果(残高・サガの状態)は`api-e2e/`のHTTPレベル
検証で既に立証済みであり、UIがその状態をどう文言化するか(「手続きできませんでした」等)
は`web-ui/src/components/TransferDetailScreen.test.tsx`がモックデータで既に検証している
(`docs/adr/0012`決定6の実装時に追加済み)。`ui-e2e/`が追加で証明すべきなのは「振込の
確認待ち状態で確認/取消ボタンが実際に表示されクリックが効くこと」「組戻すボタンが
credited後の時間窓内に実際に表示されクリックが効くこと」といった、DOM・イベント
ハンドラの配線そのもの——これはHTTPだけでは検証できない領域であり、モックAPIによる
コンポーネント単体テストでも(実際のバックエンドとの配線までは)検証できない。

## トレードオフ

- ヘッドレスブラウザテストは実AWS環境への実際のHTTPリクエスト+DOM操作+ポーリングを
  組み合わせるため、`api-e2e/`単体より1テストあたりの実行時間が長い(実測: 4テストで
  合計約30秒、並列度2)。このPoCの規模では許容範囲内と判断する。
- `support/ui.ts`は現状web-ui側にtest-id属性が無いため、実際の表示文言(ボタンラベル・
  ラベルテキスト)でセレクタを組み立てている。文言変更のたびにこのテストも追随が必要に
  なるが、意図的な選択——実際の顧客が読むのと同じ文言に依拠することで、UIの配線ドリフト
  (ボタンの文言だけ変わってハンドラの紐付けが壊れる、等)を検出できることを優先した。
- [[0006-write-path-api-gateway-sqs-direct-integration]]決定5等が確立した「独立した
  パッケージ間ではコード共有せず契約を再定義する」という方針を`ui-e2e/`にもそのまま
  適用したため、`support/stackOutputs.ts`・`support/ownerIndex.ts`は`api-e2e/`の同名
  ファイルとほぼ同じ内容の複製になっている。複製が3つ目に増えるたびにこのコストは
  積み上がるが、web-ui/api-e2e間で既に受け入れている割り切りの延長であり、新しい種類の
  トレードオフではない。

## 次のステップ

- J8相当(furikomi上限額超過)・J10相当(recall失敗)のようなドメイン却下系のUI表示
  についても、必要になれば同じ枠組みで追加できる。現時点では
  `TransferDetailScreen.test.tsx`がモックデータで同じ文言を既に検証しているため、
  優先度を上げていない。
- CI組み込みは行わない。`api-e2e/`と同じ理由(実AWS環境と実デプロイ済みスタックが要る)。
