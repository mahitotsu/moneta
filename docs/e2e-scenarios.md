# E2Eテストシナリオ一覧

## 位置づけと書き方の規約

このドキュメントは `docs/adr/` とは別の性質を持つ。ADRは「なぜその設計にしたか」の決定履歴、
こちらは「外部から見て何を保証すると約束したか」のシナリオ台帳である。将来テストの網羅性を
見直す際は、まずこのドキュメントを読めば足り、ADRまで遡る必要がないことを目指す
(ADRを読み直す必要が出た場合は、このドキュメント自体が要件の記述として不十分だったという
フィードバックとして扱う)。

- 各シナリオはGiven/When/Thenを**外部契約の言葉だけ**で書く。関数名・テーブル名・
  内部モジュール名は使わない(例外: 「何を検証したいか」を示すため、各シナリオ末尾に
  裏付けとなったADRへのリンクを付す。これは実装への参照ではなく設計根拠へのトレーサビリティ)。
- 「外部」とは、Web UI/APIクライアントから観測可能な範囲を指す:
  コマンドAPI(`PUT/POST /accounts/...`)のレスポンス、照会API
  (`GET /accounts/{id}`、`GET /accounts/{id}/transactions`)が返す内容とそのタイミング、
  Web UIの画面表示。
- 優先度は3段階。**P0**: 自動E2Eとして実装する。**P1**: 自動化するが優先度は低い、または
  手動確認と自動化を併用する。**P2**: 現時点では自動化が困難(障害注入等が必要)なため、
  手動確認のみとし、将来の自動化候補として記録に残す。

## アクター

- **顧客** (`CustomerFlow.tsx`、ダミーサインイン): 口座一覧・残高・履歴閲覧、凍結/凍結解除/解約。
- **外部チャネル** (`ChannelEmulatorScreen.tsx`、サインイン不要): ATM入出金、他行からの振込、
  収納機関への支払い。中身は`Deposit`/`Withdraw`コマンドそのもの。
- **APIクライアント(生)**: UIを介さず`Idempotency-Key`等を直接制御してコマンドAPI/照会APIを
  呼ぶ。冪等性・同時実行・検証層の境界など、UIの画面操作だけでは再現しづらいシナリオに使う。

## A. ハッピーパス(ユースケース起点)

**A1. 口座開設**
Given 未使用の口座ID、有効な初期残高
When `PUT /accounts/{id}` を呼ぶ
Then `202 Accepted` が返り、最終的に`GET /accounts/{id}`が`Active`・指定した初期残高を返す
→ [[0006-write-path-api-gateway-sqs-direct-integration]]

**A2. ATM入金 → 残高反映**
Given `Active`な口座
When 外部チャネル画面からATM入金を実行
Then `202 Accepted`が返り、最終的に残高が入金額分増加する
→ [[0009-web-ui-customer-experience-and-channel-emulation]]

**A3. ATM出金 → 残高反映**
Given 残高が出金額以上の`Active`な口座
When 外部チャネル画面からATM出金を実行
Then 最終的に残高が出金額分減少する

**A4. 他行からの振込(=Depositの別UI表現)**
Given `Active`な口座
When 外部チャネル画面から「他行からの振込」を実行
Then バックエンドの挙動はA2と同一(同じDepositコマンド)。銀行名等の表示情報はバックエンドに
送られない(リクエストボディに含まれないことを確認)
→ [[0009-web-ui-customer-experience-and-channel-emulation]]

**A5. 収納機関への支払い(=Withdrawの別UI表現)**
Given 残高が支払額以上の`Active`な口座
When 外部チャネル画面から「収納機関への支払い」を実行
Then バックエンドの挙動はA3と同一

**A6. 凍結中は入出金が拒否される**
Given `Frozen`な口座
When 外部チャネルからATM入金/出金を試みる
Then コマンド自体は`202 Accepted`されるが、最終的に残高は変化せず、口座状態は`Frozen`のまま
(却下は非同期に確定するため、UI上は「反映待ち」から「変化なし」に収束する形で観測される)
→ [[0009]] / [[0002-sqs-message-lifecycle-and-error-classification]]

**A7. 凍結解除で再度操作可能になる**
Given `Frozen`な口座
When 顧客画面から凍結解除 → 続けて外部チャネルからATM入金
Then 凍結解除後は残高が増加する(解除の反映を待ってから入金する運用が必要なことも含めて確認)

**A8. 解約後は一切の操作が拒否される**
Given `Active`な口座
When 顧客画面から解約 → その後、外部チャネルから入出金を試みる
Then 解約後は残高・状態ともに変化しない。`GET /accounts/{id}`は`Closed`・`final_balance`を返す

**A9. 取引履歴が新しい順に反映される**
Given 複数回の入出金を行った口座
When `GET /accounts/{id}/transactions` を呼ぶ
Then 最終的に全件が新しい順で返り、直近50件までであること
→ [[0009]]

## B. ドメインエラー(ユーザーに見える拒否)

`DomainError`はSQSに再試行させず、そのメッセージのトランザクション内で却下確定する
([[0002-sqs-message-lifecycle-and-error-classification]]決定1)。したがって外部からは
「`202 Accepted`は返るが、状態が変化しない・却下が最終状態になる」という形で観測される。

| ID | Given | When | Then |
|---|---|---|---|
| B1 | 残高より大きい額の出金要求 | 出金を実行 | `202`後、残高は不変(`InsufficientFunds`) |
| B2 | `Frozen`な口座 | 入金 or 出金 | 状態・残高とも不変(`AccountFrozen`) |
| B3 | `Closed`な口座 | 任意のコマンド | 状態・残高とも不変(`AccountClosed`) |
| B4 | 存在しない口座ID | 任意のコマンド | `Active`化されない(`AccountNotFound`) |
| B5 | 既にOpen済みの口座ID | 同じIDで再度`Open` | 元の状態が保持される(`AccountAlreadyExists`) |
| B6 | 既に`Active`な口座 | `Unfreeze`を実行 | 状態は`Active`のまま変化なし(`AlreadyActive`) |
| B7 | 既に`Frozen`な口座 | `Freeze`を実行 | 状態は`Frozen`のまま変化なし(`AlreadyFrozen`) |
| B8 | `Active`な口座 | 負またはゼロ額で入金/出金 | 残高不変(`InvalidAmount`)。ADR-0006決定5よりAPIGWの構造検証は正負を見ないため、ドメイン層まで到達して初めて拒否される点を確認する価値がある |

すべて優先度**P0**(ADR-0002決定1の核心的な主張であり、記事が最も検証したい性質)。

## C. 冪等性・重複配信

**C1. 同一`Idempotency-Key`での同一コマンド再送**
Given `Active`な口座
When 同じ`Idempotency-Key`で同じ入金コマンドを2回送る(クライアントのリトライを模す)
Then 残高は1回分しか増加しない
→ [[0002]]決定4 / [[0006]]決定3 — **P0**

**C2. `Idempotency-Key`ヘッダー欠落**
Given 任意の口座
When ヘッダーなしでコマンドを送る
Then APIGWレベルで`4xx`が返り、SQSまで到達しない(=状態が一切変化しない)
→ [[0006]]決定3 — **P0**

**C3. 異なる`Idempotency-Key`で同内容のコマンドを送る**
Given `Active`な口座
When 同じ入金コマンドを異なるキーで2回送る
Then 意図通り2回分反映される(重複排除が「内容」ではなく「キー」単位であることの確認)
— **P1**

## D. 同時実行・OCC競合

**D1. 同一口座への同時複数コマンド**
Given 残高が片方の出金額しか賄えない`Active`な口座
When 同一口座に対し、合計すると残高を超える2件の出金をほぼ同時に送る
Then 最終的に片方は成功・片方は`InsufficientFunds`で拒否され、残高がマイナスにならない
(直列化とOCC競合時の自動リトライが機能していることの外部観測)
→ [[0002]]決定1・決定6 — **P0**(このPoCが検証したい中心的性質)

**D2. 高頻度同時書き込みでも取りこぼしがない**
Given `Active`な口座
When 同一口座に対し10件程度の入金を同時に送る
Then 最終的に全件が反映され、合計増加額が送信した10件の合計と一致する(OCC競合が
Lambda内リトライで吸収され、クライアントからは見えないことの確認)
— **P1**(D1で本質は検証済みのため件数を増やした発展形)

## E. メッセージグループの独立性

**E1. 無関係な口座は互いに影響しない**
Given 口座A(存在しない/不正な状態)と口座B(`Active`)
When 口座Aに対して継続的に失敗するコマンドを送りつつ、同時に口座Bへ正常な入金を送る
Then 口座Aの失敗とは無関係に、口座Bへの入金は通常通り反映される
→ [[0002]]決定3(グループ単位の失敗スコープ) — **P1**
(真のヘッドオブラインブロッキング再現にはOCC競合の持続的発生が必要で自動化しづらいため、
「無関係な口座が巻き込まれない」という外部観測できる範囲に絞る)

## F. 結果整合性

**F1. コマンド直後は照会に反映されないことがある**
Given `Active`な口座
When 入金コマンド送信の直後(数秒以内)に`GET /accounts/{id}`を呼ぶ
Then 旧残高が返ることがある(失敗ではない)。ポーリングを続けると最大約1分以内に新残高に収束する
→ [[0004-query-service-event-driven-projection]]「結果整合性のトレードオフ」 — **P0**
(記事が明示的に検証したいレイテンシの実測値でもある)

**F2. 取引履歴も同様の遅延窓を持つ**
Given `Active`な口座
When 入金直後に`GET /accounts/{id}/transactions`を呼ぶ
Then 直後は反映されないことがあるが、最大約1分以内に新しいエントリが現れる

**F3. 反映待ちは失敗として表示されない**
Given 顧客画面
When 直近のコマンドがまだ照会に反映されていない状態でその口座を表示する
Then 画面は「エラー」ではなく「反映待ち」相当の表示になり、キャッシュ済みの値を優先して見せる
→ [[0001-service-boundaries-and-event-driven-integration]]のUXへの説明責任
(このプロジェクトの「結果整合性は失敗ではない」というUI方針そのものの回帰テスト) — **P0**

## G. 入力検証(APIGWレベル)

**G1. 金額が数値文字列パターン外**
Given 任意の口座
When `amount: "abc"` 等、`^-?\d+(\.\d+)?$`に一致しない値で入出金を送る
Then APIGWレベルで`4xx`、SQSに到達しない(状態不変)
→ [[0006]]決定5 — **P0**

**G2. 必須項目欠落**
Given 未使用の口座ID
When `initial_balance`を欠いた`Open`を送る
Then `4xx`が返り、口座は作られない

**G3. 未知の`FreezeReason`値**
Given `Active`な口座
When `reason`にenum外の文字列を送る
Then `4xx`で拒否される、またはG4と同じ「インフラ起因失敗としてDLQ行き」に分類されるかを
確認する(どちらの経路を通るか自体がADR-0006決定5の境界の実証になる) — **P1**

**G4. 不正な形式の`accountId`(既知のギャップの固定化)**
Given 不正な形式(UUID以外)の`accountId`
When コマンドを送る
Then クライアントには`202 Accepted`が返るが、実際には反映されない(最終的にDLQへ)
→ [[0006]]「今回のスコープ外として残す既知のギャップ」— **P1**
(バグではなく「明示的に受け入れたギャップ」であることをドキュメントする回帰テスト。
今後ここが暗黙に修正/劣化していないかを検知する意味がある)

## H. 顧客体験・チャネル分離(UI層)

**H1. 顧客向け画面に入出金ボタンが存在しない**
Given 顧客としてサインイン
When 口座詳細画面を確認する
Then Deposit/Withdrawへの導線が存在しない(UIからは外部チャネル画面を経由しないと到達できない)
→ [[0009]]決定1 — **P1**

**H2. 外部チャネル画面はサインイン不要**
Given サインインしていない状態
When 外部チャネル画面に遷移する
Then 画面が表示され、対象口座IDを直接入力して操作できる

**H3. 顧客-口座関係は端末ローカル**
Given ある端末で口座を開設し顧客に紐づける
When 別のブラウザプロファイル(=localStorageが空)で同じ顧客としてサインインする
Then 口座一覧に先ほどの口座が現れない(バックエンドに顧客概念がないことの外部観測)
→ [[0009]]決定2 — **P2**(自動化の優先度は低いが、仕様の意図的な割り切りとして記録価値がある)

## I. 持続的インフラ障害・DLQ

**I1. 持続的な障害でDLQに到達する**
Given 何らかの方法でDSQLへの書き込みを持続的に失敗させる(障害注入が必要)
When コマンドを送り続ける
Then `maxReceiveCount`超過後にFIFO DLQに到達し、CloudWatchアラームが発報する
→ [[0002]]決定6 — **P2**(自動化には障害注入基盤が要り、このPoCの規模には過大。手動確認のみ)

## J. Transfer service(口座間送金のサガ)

顧客向けUI/API Gatewayがまだ無い([[0010-transfer-service-saga]]決定6、[[0011-furikae-furikomi-distinction]]でも据え置いたまま)ため、現時点では「外部から見て何を保証するか」の記述のみで、
自動E2E化は次の増分(API Gateway追加)以降に持ち越す。それまでは`aws sqs send-message`で
Transfer受付キューへ`TransferCommand`(`{"Start":{...}}`/`{"Confirm":{...}}`/
`{"Cancel":{...}}`/`{"Recall":{...}}`のいずれか、[[0011-furikae-furikomi-distinction]])を
直接投入し、照会APIで送金元・送金先双方の残高を確認する形の手動確認が対象になる。

**J1. 正常な送金は送金元の減少・送金先の増加として反映される**
Given 送金元・送金先とも有効な口座
When 送金元の残高以下の金額で送金を要求する
Then 最終的に送金元の残高が減り、送金先の残高が同額増える
→ [[0010-transfer-service-saga]]決定3 — **P1**(API Gateway追加後にP0へ格上げ予定)

**J2. 送金元の残高不足は送金先に一切影響しない**
Given 送金元の残高より大きい金額
When 送金を要求する
Then 送金元・送金先とも残高は変化しない(出金コマンド自体がDomainErrorで却下される)
→ [[0010-transfer-service-saga]]決定3 — **P1**

**J3. 送金先が入金を受け付けられない場合、送金元へ補償される**
Given 送金先が凍結中または解約済み
When 送金元の残高以下の金額で送金を要求する
Then 送金元の残高は一時的に減った後、最終的に送金前と同額まで戻る(出金は成功、入金が
却下され補償の入金が発行される)
→ [[0010-transfer-service-saga]]決定3 — **P1**

**J4. 同一口座への送金は要求時点で却下される**
Given 送金元と送金先が同じ口座
When 送金を要求する
Then 何も実行されない(残高は変化しない)
→ [[0010-transfer-service-saga]]`start`の入力検証 — **P2**(仕様の意図的な割り切りとして記録価値がある)

**J5. 振込(名義不一致)は確認前は出金されない**
Given 送金元・送金先の名義が異なる(口座名義インデックスに双方が反映済み)
When `Start`で送金を要求する
Then サガは`pending_confirmation`のまま停止し、送金元・送金先とも残高は変化しない
(account-serviceには何も発行されていない)
→ [[0011-furikae-furikomi-distinction]]決定3 — **P1**(API Gateway追加後にP0へ格上げ予定)

**J6. 振込を確認すると出金→着金が進む**
Given J5の状態(`pending_confirmation`)
When 同じ`transfer_id`で`Confirm`を要求する
Then 最終的に送金元の残高が減り、送金先の残高が同額増える(J1と同じ最終結果)
→ [[0011-furikae-furikomi-distinction]]決定3 — **P1**

**J7. 振替(名義一致)は確認不要で即座に開始される**
Given 送金元・送金先の名義が同じ
When `Start`で送金を要求する
Then `Confirm`を待たずに出金コマンドが発行され、J1と同じ結果に至る
→ [[0011-furikae-furikomi-distinction]]決定1・決定3 — **P1**

**J8. Furikomiの上限額超過は受付時点で却下される**
Given 送金元・送金先の名義が異なる
When 上限額を超える金額で`Start`を要求する
Then サガは作成されず、送金元・送金先とも残高は変化しない
→ [[0011-furikae-furikomi-distinction]]決定4 — **P2**

**J9. Credited済みFurikomiを期限内にrecallすると組戻しされる**
Given J6が完了した(`credited`)振込のサガ
When 期限内に`Recall`(新しい`transfer_id`・元の`transfer_id`を指定)を要求する
Then 最終的に送金先の残高が減り、送金元の残高が同額戻る(逆方向の送金として実行される)
→ [[0011-furikae-furikomi-distinction]]決定5 — **P2**

**J10. 期限超過または受取人の残高不足でのrecallはFailedになる**
Given J9の状態で、時間窓を過ぎている、または送金先の残高が送金額未満
When `Recall`を要求する
Then 期限超過の場合は却下されサガは作成されない/残高不足の場合は組戻し用サガが
`failed`になり、送金先の残高は変化しない
→ [[0011-furikae-furikomi-distinction]]決定5 — **P2**

## 次のステップ

- P0だけでも15シナリオ程度あり、これがE2E自動化の最初のスコープ候補になる。
- D1・F1はこのPoCの核心的な技術主張(OCC直列化・結果整合性)を直接裏付けるため、実装の
  優先順位はここを最初に置くことを推奨する。
- 自動化の実行方式(実AWS環境に対して叩くのか、docker-composeでSQS/DynamoDBをローカルに
  立てるのか等)は別途検討が必要。`clean-data.ts`の存在から見て、実環境に対してテストごとに
  状態をリセットする方針が既に志向されている可能性がある。
